Guía Técnica del Framework de Automatización

Documento de apoyo para explicar cómo está construida la herramienta de automatización del proyecto Versia Renal, cómo se organiza el código, cómo se ejecutan los escenarios, cómo se generan evidencias y qué aporta cada decisión técnica del framework.

Resumen

Este documento está pensado para una exposición técnica. La idea es poder leerlo en una pantalla mientras en la otra se muestra IntelliJ, el navegador, los reports o Azure Test Plans. No sustituye la documentación funcional: explica cómo funciona la herramienta de automatización por dentro.

Mensaje principal: el framework permite transformar test cases manuales en escenarios automatizados mantenibles, separando lenguaje de negocio, pasos técnicos, acciones de pantalla, utilidades comunes y evidencias.

1. Objetivo técnico

El objetivo del framework es automatizar pruebas funcionales end-to-end del producto Versia Renal. La automatización ejecuta el navegador, inicia sesión, navega por la aplicación, interactúa con formularios y valida que el resultado esperado se cumple.

El framework no es solo una colección de scripts. Está organizado para que el trabajo sea mantenible: si cambia una pantalla, se modifica principalmente su Page; si cambia el caso de prueba, se modifica el Feature; si se necesita una acción común, se coloca en BasePage.

Lectura sugerida: "La herramienta separa el lenguaje del caso de prueba de la implementación técnica. Esto permite que un escenario sea legible para QA, pero que internamente Selenium ejecute las acciones reales sobre la aplicación."

2. Tecnologías utilizadas

Antes de entrar en la estructura del proyecto, es importante entender las tecnologías que forman la base del framework. Cada una cubre una parte concreta: lenguaje, ejecución, automatización del navegador, escritura de escenarios, configuración y generación de evidencias.

Tecnología Uso dentro del framework
Java Lenguaje principal. Aquí se implementan steps, Pages, utilidades y lógica de automatización.
Maven Gestiona dependencias, compilación y ejecución de pruebas desde el archivo pom.xml.
Selenium WebDriver Controla el navegador: clicks, escritura en campos, navegación, iframes, alertas y validaciones visuales.
Cucumber Conecta escenarios escritos en Gherkin con métodos Java mediante steps.
Gherkin Lenguaje de los archivos Feature. Permite describir casos con Given, When y Then.
Spring / Spring Boot Gestiona contexto, inyección de dependencias y configuración compartida entre Pages, Steps y utilidades.
JUnit Permite lanzar la suite de pruebas y conectar la ejecución con Cucumber.
Extent Reports Genera reportes HTML con escenarios, pasos ejecutados, resultados y evidencias.
application.properties Centraliza URL, credenciales por clave, navegador, timeouts y rutas de ejecución.
WebDriverManager / ChromeDriver Prepara el driver del navegador para que Selenium pueda abrir y controlar Chrome.

El papel del pom.xml

El archivo pom.xml es el archivo principal de Maven. Define cómo se construye el proyecto, qué dependencias necesita y cómo se ejecutan las pruebas. Cuando se abre el framework en IntelliJ, Maven lee este archivo y descarga las librerías necesarias para que Java, Selenium, Cucumber, Spring y los reportes funcionen correctamente.

También permite ejecutar el framework desde terminal con comandos mvn, sin tener que configurar manualmente cada librería. Por eso el proyecto siempre debe abrirse desde la carpeta raíz donde está el pom.xml.

Lectura sugerida: "El framework está construido principalmente con Java, Maven, Selenium, Cucumber, Gherkin y Spring. Java contiene la lógica, Maven gestiona el proyecto, Selenium controla el navegador, Cucumber conecta los escenarios con código Java, y Spring ayuda a organizar e inyectar las clases que se usan durante la ejecución."

3. Programación orientada a aspectos

El framework usa programación orientada a aspectos para ejecutar lógica transversal sin meterla manualmente en cada step. En automatización esto se usa principalmente para evidencias, por ejemplo capturas de pantalla asociadas a pasos ejecutados.

Una lógica transversal es una acción que afecta a muchos puntos del sistema: logging, capturas, medición de tiempos o reporting. Si se pusiera manualmente en cada step, habría mucha repetición y sería fácil olvidarlo.

Por qué se explica al inicio

Antes de enseñar carpetas y clases conviene entender esta idea: el framework separa la prueba funcional de las tareas comunes que rodean a la prueba. Por eso existen capas, métodos reutilizables y evidencias automáticas. La estructura del proyecto tiene sentido cuando se entiende primero esa separación.

Comparación técnica

Sin AOP Con AOP
El código de captura se repite en muchos steps. La captura se dispara desde una regla común.
Mayor riesgo de olvidar evidencias. La evidencia se genera de forma más consistente.
Los steps mezclan lógica funcional y lógica de reporte. Los steps se mantienen enfocados en la acción de negocio.
La idea clave es separar lo que se prueba de cómo se registra la evidencia.

4. Estructura del proyecto

El proyecto sigue una estructura típica de automatización Java con Cucumber, Selenium y Spring. Las carpetas más importantes son:

Ruta Uso Cómo explicarlo
src/test/java/.../cucumber/features Contiene los escenarios escritos en Gherkin. Es la capa legible del test case: Given, When, Then.
src/test/java/.../cucumber/steps Implementa los steps de Cucumber en Java. Traduce cada frase Gherkin a una llamada Java.
src/test/java/.../pages/baxter_page Contiene las Page Objects de cada módulo. Aquí viven los XPaths y acciones de pantalla.
src/test/java/.../pages/BasePage.java Clase base con acciones reutilizables. Evita duplicar esperas, clicks, manejo de alertas y dropdowns.
src/test/java/.../configuration Configuración de WebDriver, waits y contexto Spring. Define cómo se crea el navegador y las dependencias.
src/test/java/.../aspect_oriented_programming Aspectos para capturar evidencias. Permite ejecutar lógica transversal sin repetirla en cada test.
src/test/resources/application.properties URL, credenciales, navegador y parámetros de ejecución. Centraliza datos de entorno y evita hardcodear en los tests.
target/reports Reports generados después de ejecutar. Sirve para revisar resultado, pasos ejecutados y fallos.

5. Flujo Feature - Steps - Page

El flujo principal del framework tiene tres capas. Esta separación es clave para explicar el diseño:

  1. Feature: describe el escenario en lenguaje Gherkin.
  2. Steps: enlaza cada frase del Feature con código Java.
  3. Page: ejecuta la acción real con Selenium sobre el DOM.

Ejemplo de flujo

Feature:
When I click messages icon

Steps:
@When("I click messages icon")
public void iClickMessagesIcon() throws InterruptedException {
    messagesPage.clickMessagesIcon();
}

Page:
public void clickMessagesIcon() throws InterruptedException {
    driver.switchTo().defaultContent();
    waitElements(btnMessagesIcon);
    clickJS(btnMessagesIcon);
}
Este patrón permite que el Feature se mantenga limpio, que los Steps sean reutilizables y que los detalles del DOM estén concentrados en la Page.

6. BasePage

BasePage es una pieza central. Todas las Page Objects heredan de esta clase. Su función es ofrecer métodos comunes para que cada módulo no repita la misma lógica.

Qué aporta BasePage

  • Escritura en inputs con write(...).
  • Clicks normales y clicks JavaScript.
  • Esperas explícitas con WebDriverWait.
  • Scroll a elementos antes de interactuar.
  • Manejo de alertas del navegador: aceptar o cancelar.
  • Manejo de dropdowns Kendo reutilizable.
  • Funciones auxiliares para modales, textos y acciones comunes.

Por qué es importante

Si cada Page implementara su propio click, su propia espera o su propio método de Kendo, el framework crecería con duplicación y sería más difícil de mantener. La BasePage hace que las acciones comunes tengan una sola fuente de verdad.

Lectura sugerida: "BasePage es la capa común de Selenium. Nos permite normalizar cómo esperamos elementos, cómo hacemos click, cómo seleccionamos opciones y cómo evitamos repetir código en cada módulo."

7. Properties y configuración

El archivo application.properties centraliza valores que no deberían estar repartidos por los Features o las Pages. Por ejemplo:

  • URL base de la aplicación.
  • Usuarios y contraseñas por clave.
  • Navegador usado para ejecutar.
  • Timeouts y rutas de evidencias.

Ejemplo de credenciales

application.users={login_baxter:'support', login_baxter_t:'trasplante'}
application.passwords={login_baxter:'renal2', login_baxter_t:'trasplante'}

En un Feature no se escribe el usuario real. Se escribe la clave: 

And I try to login with "login_baxter_t" credentials

El step recibe login_baxter_t, la Page busca esa clave en los mapas de usuarios y contraseñas, y Selenium escribe los valores reales en la pantalla.

Esto permite cambiar credenciales o entorno sin modificar todos los escenarios.

8. XPaths desde el DOM

Los XPaths son localizadores que permiten a Selenium encontrar elementos en el DOM. Un buen XPath debe ser estable, legible y lo bastante específico para no coger otro elemento.

Cómo conseguir un XPath desde el DOM

  1. Abrir la pantalla en el navegador.
  2. Pulsar F12 o inspeccionar el elemento.
  3. Buscar un texto estable, un id, una clase o un componente padre reconocible.
  4. Construir el XPath tomando un padre claro y luego el hijo que se necesita.
  5. Probarlo en consola con $x("...").
  6. Evitar XPaths absolutos con muchas posiciones si hay una alternativa estable.

Ejemplos recomendables

La forma más sencilla es localizar primero un texto padre claro y después buscar el hijo que interesa. Si el DOM tiene un título como Medication, Messages o Contacts, se usa ese título como referencia y se baja al botón, icono, input o fila que está dentro del mismo bloque. 

//h2[text()='Medication']//span[contains(@class,'k-icon')]
//h2[text()='Messages']//button[contains(@class,'k-grid-add')]
//h2[text()='Contacts']//button[contains(@class,'k-grid-edit')]

Cuando el botón no es hijo directo del título, se sube al panel padre y luego se busca el hijo dentro de ese panel: 

//h2[text()='Messages']/ancestor::div[contains(@class,'x_panel')]//button[contains(@class,'k-grid-add')]
//h2[text()='Contacts']/ancestor::div[contains(@class,'x_panel')]//button[contains(@class,'k-grid-edit')]

Para una tabla, se puede localizar la fila por texto visible y desde esa fila coger el botón de acción: 

//tr[.//td[contains(text(),'Foianini Baggio')]]//button[contains(@class,'k-grid-edit')]
//tr[.//td[contains(text(),'qatest@vantive.com')]]//button[contains(@class,'k-grid-delete')]

Si el elemento tiene un atributo estable, se puede usar directamente: 

//textarea[@name='textoNotificacion']
//input[@name='fechaFin']
//button[contains(@class,'k-grid-cancel')]

Estos XPaths son mejores que usar una ruta absoluta como: 

/html/body/div[3]/div[1]/div[4]/div/div[2]/ul/li[1]

Reglas prácticas

  • Usar textos visibles cuando son estables: normalize-space(.)='Messages'.
  • Usar un contenedor padre claro: título, panel, tabla o formulario.
  • Evitar ids dinámicos generados por Kendo o Angular si cambian entre ejecuciones.
  • Si hay muchos botones iguales, localizar primero el panel y luego el botón.
  • Para Kendo, buscar el wrapper visible, no el select oculto.
Lectura sugerida: "No se trata de copiar cualquier XPath del navegador. Intentamos construir XPaths mantenibles, usando un título o panel como padre y después el elemento concreto que necesitamos."

9. Iframes, alertas y modales

Versia Renal usa iframes en varios módulos. Selenium solo puede interactuar con elementos del contexto actual. Por eso, antes de buscar un elemento dentro del módulo hay que entrar al iframe correcto.

Patrón habitual

driver.switchTo().frame("frmContenido");
// acciones dentro del módulo
driver.switchTo().parentFrame();

driver.switchTo().frame("frmContenido") cambia el contexto de Selenium: desde ese momento los botones, inputs y tablas se buscan dentro de ese iframe. Al terminar, driver.switchTo().parentFrame() vuelve un nivel hacia fuera. Si no se sale, el siguiente step puede fallar porque Selenium seguirá buscando dentro del módulo anterior.

Si hay dos iframes, se entra dos veces y se sale dos veces: 

driver.switchTo().frame("frmContenido");
driver.switchTo().frame("iframeV2");
// acciones dentro del formulario
driver.switchTo().parentFrame();
driver.switchTo().parentFrame();

La regla práctica es simétrica: cada entrada a un iframe debe tener su salida. Esto deja el navegador preparado para el siguiente step.

Alertas

Hay dos tipos de alertas:

  • Alertas del navegador: ventanas nativas tipo aceptar/cancelar.
  • Modales de la aplicación: HTML dentro de la página o dentro de iframe.

Las alertas nativas se gestionan con driver.switchTo().alert() o métodos comunes como acceptBrowserAlert() y dismissBrowserAlert(). Los modales HTML se tratan como elementos normales del DOM.

10. Reports y evidencias

Después de ejecutar, el framework genera reportes que sirven para demostrar qué escenario se lanzó, qué pasos pasaron, cuál falló y qué captura quedó asociada.

Elemento Uso
target/reports/VersiaRenal-ExtentReport.html Reporte visual de ejecución con estado de escenarios y steps.
target/reports/cucumber-report.xml Resultado estructurado de Cucumber, útil para CI o análisis técnico.
target/screenshots Capturas generadas durante la ejecución, especialmente en fallos.
src/test/resources/screenshots/test-execution.log Log de ejecución con trazas útiles para depurar.
Los reports, logs y archivos de target son generados por ejecución. Sirven para revisar, pero normalmente no se suben al repositorio como cambios funcionales.

11. Ejemplo real: módulo Messages

El módulo Messages es un buen ejemplo para explicar el flujo completo porque incluye: icono fuera de iframe, navegación al módulo, panel de mensajes dentro de iframe, tabs, contador de mensajes y formulario de creación.

Feature

Scenario: View unread received message from messages icon

  And   I try to login with "login_baxter_t" credentials
  And   I login successful
  Then  I verify messages icon badge is greater than 1
  When  I click messages icon
  And   I click see all messages

Qué demuestra este caso

  • Uso de credenciales por clave desde properties.
  • Validación del contador del icono sin depender de un número exacto.
  • Click en un menú desplegable fuera de iframe.
  • Entrada al iframe frmContenido para trabajar dentro del módulo.
  • Verificación flexible del panel de mensajes recibidos.

12. Puntos clave de la explicación

Tema Explicación para la exposición
Cucumber Porque permite expresar casos en lenguaje legible y conectar esos pasos con automatización real.
Separación Feature, Steps y Page Porque cada capa tiene una responsabilidad: negocio, traducción técnica y acciones de pantalla.
BasePage Para centralizar acciones repetidas y mantener consistencia en esperas, clicks, alertas y Kendo.
Reports generados Porque son artefactos generados por ejecución; el repositorio debe contener código fuente y features.
XPaths Se construyen desde un padre estable y se evita depender de posiciones o ids dinámicos.
Evidencias Permiten demostrar qué se ejecutó, dónde falló y qué veía el navegador en ese momento.
